\section{Ejercicio 2}
Se diseñó y ejecutó una batería de pruebas para \texttt{numberOfOcurrences(List<Integer> l, Integer element)} utilizando \textit{Input Space Partitioning} y cobertura \textit{pairwise}.

\subsection{Archivos trabajados}
\begin{itemize}
  \item \texttt{src/main/java/assignment3\_exercises/ListUtils.java}
  \item \texttt{src/test/java/assignment3\_exercises/numberOfOcurrencesTest.java}
\end{itemize}

\subsection{Modelo del Dominio de Entradas (MDE)}
Características y bloques:
\begin{itemize}
  \item C1 (referencia de \texttt{l}): L0 = \texttt{null}, L1 = no \texttt{null}.
  \item C2 (referencia de \texttt{element}): E0 = \texttt{null}, E1 = no \texttt{null}.
  \item C3 (tamaño de lista, si L1): S0 = vacía, S1 = no vacía.
  \item C4 (ocurrencias, si L1 y E1): O0 = 0, O1 = 1, O2 = más de 1.
\end{itemize}

Restricciones:
\begin{itemize}
  \item Si L0, C3 y C4 no aplican.
  \item Si E0, C4 no aplica.
  \item Si S0, necesariamente O0.
\end{itemize}

\subsection{Requisitos de test para Pairwise Coverage (PWC)}
\begin{itemize}
  \item R01: (L0, E0)
  \item R02: (L0, E1)
  \item R03: (L1, E0)
  \item R04: (L1, E1)
  \item R05: (L1, S0)
  \item R06: (L1, S1)
  \item R07: (L1, O0)
  \item R08: (L1, O1)
  \item R09: (L1, O2)
  \item R10: (E0, S0)
  \item R11: (E0, S1)
  \item R12: (E1, S0)
  \item R13: (E1, S1)
  \item R14: (E1, O0)
  \item R15: (E1, O1)
  \item R16: (E1, O2)
  \item R17: (S0, O0)
  \item R18: (S1, O0)
  \item R19: (S1, O1)
  \item R20: (S1, O2)
\end{itemize}

\subsection{Casos implementados}
\begin{itemize}
  \item TC1: \texttt{l = null}, \texttt{element = null} $\rightarrow$ \texttt{IllegalArgumentException} (R01).
  \item TC2: \texttt{l = null}, \texttt{element = 7} $\rightarrow$ \texttt{IllegalArgumentException} (R02).
  \item TC3: \texttt{l = []}, \texttt{element = null} $\rightarrow$ \texttt{IllegalArgumentException} (R03, R05, R10).
  \item TC4: \texttt{l = [1,2,3]}, \texttt{element = null} $\rightarrow$ \texttt{IllegalArgumentException} (R03, R06, R11).
  \item TC5: \texttt{l = []}, \texttt{element = 5} $\rightarrow$ \texttt{0} (R04, R05, R07, R12, R14, R17).
  \item TC6: \texttt{l = [1,2,3]}, \texttt{element = 9} $\rightarrow$ \texttt{0} (R04, R06, R07, R13, R14, R18).
  \item TC7: \texttt{l = [1,2,3]}, \texttt{element = 2} $\rightarrow$ \texttt{1} (R04, R06, R08, R13, R15, R19).
  \item TC8: \texttt{l = [4,1,4,4]}, \texttt{element = 4} $\rightarrow$ \texttt{3} (R04, R06, R09, R13, R16, R20).
\end{itemize}

Además, se incorporó un caso de robustez para verificar que la lista de entrada no sea modificada por la rutina.

\subsection{Implementación}
La implementación en \texttt{ListUtils.numberOfOcurrences} valida precondiciones y luego contabiliza coincidencias con \texttt{element.equals(actual)}.

\subsection{Ejecución}
\begin{lstlisting}[style=codestyle]
mvn -Dmaven.repo.local=.m2 -Dtest=numberOfOcurrencesTest test
\end{lstlisting}

\section{Ejercicio 3}
Se analizó el MDE propuesto para \texttt{SetUtils.intersection(Set<Integer> set1, Set<Integer> set2)} y se diseñó una suite de pruebas con criterio \textit{Base Choice}.

\subsection{Archivos trabajados}
\begin{itemize}
  \item \texttt{src/main/java/assignment3\_exercises/SetUtils.java}
  \item \texttt{src/test/java/assignment3\_exercises/IntersectionTest.java}
\end{itemize}

\subsection{Análisis del modelo original}
\subsubsection*{a) Completitud de C1 (y análogamente C2)}
Sí, es completa: para \texttt{set1} las opciones son \texttt{null}, vacío o no vacío, y esos casos quedan cubiertos.

\subsubsection*{b) No solapamiento de C1 (y análogamente C2)}
Sí, no hay solapamiento: un set no puede ser simultáneamente \texttt{null}, vacío y no vacío.

\subsubsection*{c) Completitud de C3}
No se cumple. Contraejemplo:
\[
set1 = \{1,2\}, \quad set2 = \{2,3\}
\]
La intersección no es vacía, pero no son iguales ni subconjuntos entre sí, y tampoco son disjuntos.

\subsubsection*{d) Disyunción de C3}
Tampoco se cumple. Contraejemplo:
\[
set1 = set2 = \{1,2\}
\]
Si ``subconjunto'' no se restringe a subconjunto propio, la entrada cae a la vez en ``iguales'' y en ``set1 subconjunto de set2''.

\subsection{MDE corregido}
\begin{itemize}
  \item C1: \texttt{set1 == null}, \texttt{set1 = \{\}}, \texttt{set1} no vacío.
  \item C2: \texttt{set2 == null}, \texttt{set2 = \{\}}, \texttt{set2} no vacío.
  \item C3 (solo si C1 y C2 no nulos):
  \begin{itemize}
    \item C3.b1: \texttt{set1 = set2}
    \item C3.b2: \texttt{set1} subconjunto propio de \texttt{set2}
    \item C3.b3: \texttt{set2} subconjunto propio de \texttt{set1}
    \item C3.b4: disjuntos
    \item C3.b5: solapamiento parcial (intersección no vacía y sin inclusión)
  \end{itemize}
\end{itemize}

Con esta revisión, C3 resulta completa y disyunta.

\subsection{Base Choice (BC): requisitos y casos}
Bloques base elegidos:
\begin{itemize}
  \item C1 base: set1 no vacío.
  \item C2 base: set2 no vacío.
  \item C3 base: conjuntos iguales.
\end{itemize}

Requisitos BC considerados:
\begin{itemize}
  \item TR-BC1: caso base.
  \item TR-BC2: variar C1 a \texttt{null} $\rightarrow$ \texttt{NullPointerException}.
  \item TR-BC3: variar C1 a vacío (ajustado por factibilidad).
  \item TR-BC4: variar C2 a \texttt{null} $\rightarrow$ \texttt{NullPointerException}.
  \item TR-BC5: variar C2 a vacío (ajustado por factibilidad).
  \item TR-BC6: variar C3 a ``set1 subconjunto propio de set2''.
  \item TR-BC7: variar C3 a ``set2 subconjunto propio de set1''.
  \item TR-BC8: variar C3 a disjuntos.
  \item TR-BC9: variar C3 a solapamiento parcial.
\end{itemize}

Los casos \texttt{TC1} a \texttt{TC9} de \texttt{IntersectionTest} cubren estos requisitos y agregan, además, validaciones de no mutación de entradas, nueva instancia de retorno y borde con ambos conjuntos vacíos.

\subsection{Implementación}
\texttt{SetUtils.intersection} se implementó para:
\begin{itemize}
  \item lanzar \texttt{NullPointerException} ante entradas \texttt{null},
  \item devolver un nuevo \texttt{Set} con la intersección,
  \item no modificar los conjuntos recibidos.
\end{itemize}

\subsection{Ejecución}
\begin{lstlisting}[style=codestyle]
mvn -Dmaven.repo.local=.m2 -Dtest=IntersectionTest test
\end{lstlisting}

\section{Ejercicio 4}
Se modeló y probó el método \texttt{PatternIndex.patternIndex(String subject, String pattern)} aplicando cobertura \textit{pairwise} con restricciones de factibilidad.

\subsection{Archivos trabajados}
\begin{itemize}
  \item \texttt{src/main/java/assignment3\_exercises/PatternIndex.java}
  \item \texttt{src/test/java/assignment3\_exercises/PatternIndexTest.java}
\end{itemize}

\subsection{Modelo del Dominio de Entradas (MDE)}
\begin{itemize}
  \item C1: referencia de \texttt{subject} (\texttt{null} / no \texttt{null}).
  \item C2: referencia de \texttt{pattern} (\texttt{null} / no \texttt{null}).
  \item C3: tamaño de \texttt{subject} (vacío / no vacío), si C1 no es \texttt{null}.
  \item C4: tamaño de \texttt{pattern} (vacío / 1 carácter / 2 o más), si C2 no es \texttt{null}.
  \item C5: tipo de resultado (índice inicial / intermedio / final / \texttt{-1}), si C1 y C2 no son \texttt{null}.
\end{itemize}

Restricciones destacadas:
\begin{itemize}
  \item Si C1 o C2 es \texttt{null}, se espera excepción y C3--C5 no aplican.
  \item Si \texttt{pattern} es vacía, el resultado esperado es \texttt{0}.
  \item Si \texttt{subject} es vacía y \texttt{pattern} no vacía, el resultado esperado es \texttt{-1}.
\end{itemize}

\subsection{Requisitos pairwise y casos de prueba}
Se definieron 20 requisitos de cobertura por pares (R01--R20) y se implementaron 15 casos (TC1--TC15) que cubren:
\begin{itemize}
  \item validación de precondiciones en entradas \texttt{null},
  \item patrón vacío,
  \item coincidencia al inicio, medio y final,
  \item patrón no encontrado,
  \item sujeto vacío con patrón no vacío.
\end{itemize}

\subsection{Defectos observados en la versión original}
La batería de tests permite evidenciar dos problemas clásicos en la implementación base:
\begin{itemize}
  \item ausencia de validación de \texttt{null} según especificación,
  \item manejo incorrecto del caso \texttt{pattern} vacía.
\end{itemize}

\subsection{Corrección documentada}
La corrección aplicada/esperada para satisfacer la especificación es:
\begin{lstlisting}[style=codestyle,language=Java]
if (subject == null || pattern == null) {
    throw new IllegalArgumentException(...);
}
if (pattern.isEmpty()) {
    return 0;
}
if (pattern.length() > subject.length()) {
    return -1;
}
// buscar primera ocurrencia y devolver su indice
\end{lstlisting}

\subsection{Ejecución}
\begin{lstlisting}[style=codestyle]
mvn -Dmaven.repo.local=.m2 -Dtest=PatternIndexTest test
\end{lstlisting}

\section{Ejercicio 5}
Se diseñaron pruebas sobre \texttt{Iterator} de \texttt{ArrayList} a partir de la especificación oficial de Java, aplicando modelado de características y cobertura de pares.

\subsection{Referencia}
\begin{itemize}
  \item Oracle Java SE 7, \texttt{java.util.Iterator}: \url{https://docs.oracle.com/javase/7/docs/api/java/util/Iterator.html}
\end{itemize}

Puntos de especificación utilizados:
\begin{itemize}
  \item \texttt{hasNext()} informa si existe próximo elemento.
  \item \texttt{next()} devuelve el siguiente elemento o lanza \texttt{NoSuchElementException}.
  \item \texttt{remove()} es opcional.
  \item \texttt{remove()} lanza \texttt{UnsupportedOperationException} si no está soportado.
  \item \texttt{remove()} lanza \texttt{IllegalStateException} si se viola su precondición de uso.
\end{itemize}

\subsection{Archivos trabajados}
\begin{itemize}
  \item \texttt{src/test/java/assignment3\_exercises/IteratorArrayListTest.java}
\end{itemize}

\subsection{MDE utilizado}
Características modeladas:
\begin{itemize}
  \item C1: el iterador tiene más valores \{\texttt{true}, \texttt{false}\}.
  \item C2: \texttt{next()} retorna objeto no \texttt{null} \{\texttt{true}, \texttt{false}\}.
  \item C3: \texttt{remove()} soportado \{\texttt{true}, \texttt{false}\}.
  \item C4: restricción de \texttt{remove()} satisfecha \{\texttt{true}, \texttt{false}\}.
\end{itemize}

Decisiones de instanciación:
\begin{itemize}
  \item C3=\texttt{true}: \texttt{ArrayList.iterator()}.
  \item C3=\texttt{false}: \texttt{Collections.unmodifiableList(...).iterator()}.
\end{itemize}

\subsection{Cobertura y suite implementada}
Se cubrieron 13 requisitos (R01--R13) mediante casos \texttt{TC1} a \texttt{TC13}, contemplando:
\begin{itemize}
  \item estados de \texttt{hasNext()} en iterador con datos, vacío y agotado,
  \item \texttt{next()} con retorno no nulo, retorno nulo y excepción por agotamiento,
  \item \texttt{remove()} no soportado,
  \item \texttt{remove()} con precondición inválida,
  \item \texttt{remove()} exitoso con y sin elementos remanentes.
\end{itemize}

\subsection{Resultado}
En los escenarios modelados no se identificaron inconsistencias respecto de la especificación de \texttt{Iterator}. La suite confirma el comportamiento esperado tanto en caminos válidos como en excepciones contractuales.

\subsection{Ejecución}
\begin{lstlisting}[style=codestyle]
mvn -Dmaven.repo.local=.m2 -Dtest=IteratorArrayListTest test
\end{lstlisting}

\section*{Conclusiones}
\addcontentsline{toc}{section}{Conclusiones}
La resolución del Práctico 3 consolidó el trabajo con \textit{Input Space Partitioning} aplicado a problemas concretos de especificación, modelado y diseño de pruebas. El uso combinado de \textit{Pairwise Coverage} y \textit{Base Choice} permitió estructurar suites justificadas por requisitos explícitos, reducir redundancia y mantener trazabilidad entre modelo, casos y comportamiento esperado.
