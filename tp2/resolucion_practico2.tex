\section*{Introducción}
\addcontentsline{toc}{section}{Introducción}
Este documento reúne la resolución del \textit{Práctico 2} de \textit{Testing de Software 2024}. La consigna profundiza en testing automatizado con JUnit 5, en particular en el enfoque \textit{data-driven} a través de la anotación \texttt{@ParameterizedTest} y sus distintas fuentes (\texttt{@CsvSource}, \texttt{@MethodSource}, \texttt{@CsvFileSource}). También introduce la idea de \textit{invariante de representación} y el método \texttt{repOK()} como oráculo interno, aplicado a dos tipos de datos abstractos clásicos: una pila acotada (\texttt{StackAr}) y una cola circular acotada (\texttt{BoundedQueue}). Por último, se rescata un caso real de defecto, el \textit{Zune bug}, como excusa para practicar debugging guiado por tests.

El práctico se apoya en los conceptos del capítulo 3 del libro de Ammann y Offutt, en particular en el patrón \textit{arrange-act-assert} y en la idea de definir criterios de cobertura y oráculos de manera explícita. Para acompañar el estudio, se incluye un resumen teórico separado (\texttt{resumen\_teorico\_tp2.tex}) basado en la carpeta \texttt{material/}.

A lo largo del documento se asume que el lector está familiarizado con los conceptos básicos vistos en el TP1: \textit{fault}, \textit{error}, \textit{failure} y el modelo RIPR.

\section{Ejercicio 1}
\subsection{Lectura}
Lectura del capítulo 3 de \textit{Introduction to Software Testing} (Ammann y Offutt, 2da edición), titulado \textit{Test Automation}. Las ideas más relevantes para el resto del práctico son:
\begin{itemize}
  \item Distinción entre \textbf{Test Requirement} (TR) y \textbf{Test Coverage Criterion} (TCC). Un TR es una propiedad que un test debe satisfacer; un TCC es una regla que, dado un artefacto bajo prueba, genera el conjunto de TRs a cubrir.
  \item Noción de \textbf{subsumption} entre criterios: $C_1$ subsume a $C_2$ si todo test set que cubre $C_1$ también cubre $C_2$.
  \item Patrón \textbf{arrange / act / assert} para tests automatizados, separación de \textit{fixtures}, drivers y stubs.
  \item Idea de \textit{Test-Driven Development} como técnica de diseño.
  \item Marco \textbf{Model-Driven Test Design (MDTD)}: aplicar los mismos criterios a cuatro modelos --- control flow, data flow, logic, input space --- usando una capa de abstracción intermedia.
\end{itemize}
El resumen teórico que acompaña este informe (sección final del repositorio) reorganiza estas ideas con más detalle.

\section{Ejercicio 2}
\subsection{Objetivo}
Reescribir los tests del ejercicio 3 del Práctico 1 como tests parametrizados sobre la clase
\begin{center}
\texttt{assignment2\_exercises.SimpleRoutines}
\end{center}
La consigna exige usar al menos un \texttt{@MethodSource} y al menos un caso en formato CSV (\texttt{@CsvSource} o \texttt{@CsvFileSource}).

\subsection{Estrategia de parametrización}
Cada método se prueba con una fuente distinta, lo que permite ilustrar las tres alternativas principales que provee JUnit~5:
\begin{itemize}
  \item \texttt{findLast}: \texttt{@CsvSource} \textit{inline} en el código.
  \item \texttt{lastZero}, \texttt{countPositive}: \texttt{@MethodSource}, porque conviene devolver \texttt{int[]} directamente.
  \item \texttt{oddOrPos}: \texttt{@CsvFileSource}, leyendo el archivo \texttt{odd\_or\_pos\_cases.csv} desde \texttt{src/test/}\allowbreak\texttt{resources}.
\end{itemize}

\subsection{Casos elegidos y modelo RIPR}
La selección de casos sigue el análisis del TP1. Para cada uno de los cuatro programas se incluyen tanto un caso (c) --- ejecuta el defecto pero no produce falla --- como un caso (d) --- ejecuta el defecto y produce falla observable. Para \texttt{countPositive} y \texttt{oddOrPos} se incluye también el caso (b) (arreglo vacío), donde el defecto ni siquiera se alcanza.

\begin{center}
\begin{tabular}{lll}
\toprule
Programa & Caso (c) (pasa) & Caso (d) (revela el defecto) \\
\midrule
\texttt{findLast}      & \texttt{[5,2,3], 2 -> 1}  & \texttt{[2,3,5], 2 -> 0}      \\
\texttt{lastZero}      & \texttt{[1,0,2] -> 1}     & \texttt{[0,1,0] -> 2}         \\
\texttt{countPositive} & \texttt{[-4,2,2] -> 2}    & \texttt{[-4,2,0,2] -> 2}      \\
\texttt{oddOrPos}      & \texttt{[2,4,-2] -> 2}    & \texttt{[-3,-2,0,1,4] -> 3}   \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Implementación abreviada}
\begin{lstlisting}[style=javastyle]

@CsvSource({

    "'2,3,5', 2, 0"

@ParameterizedTest(name = "lastZero({0}) -> {1}")
@MethodSource("lastZeroCases")

    assertEquals(esperado, SimpleRoutines.lastZero(entrada));

@ParameterizedTest(name = "oddOrPos({0}) -> {1}")
@CsvFileSource(resources = "/assignment2_exercises/odd_or_pos_cases.csv", numLinesToSkip = 1)

    assertEquals(esperado, SimpleRoutines.oddOrPos(parseArray(valores)));
}
\end{lstlisting}

\subsection{Resultado sobre la versión defectuosa}
La clase \texttt{SimpleRoutines} provista por la cátedra para este práctico es la versión \textit{con} los cuatro defectos del TP1. Cuando se ejecuta la suite parametrizada se obtienen exactamente cuatro \textit{failures}, uno por programa, correspondientes a los casos (d):
\begin{itemize}
  \item \texttt{findLast([2,3,5], 2)} devuelve \texttt{-1} en lugar de \texttt{0} (la guarda \texttt{i > 0} omite el índice cero).
  \item \texttt{lastZero([0,1,0])} devuelve \texttt{0} en lugar de \texttt{2} (recorre de izquierda a derecha y se queda con el primer cero).
  \item \texttt{countPositive([-4,2,0,2])} devuelve \texttt{3} en lugar de \texttt{2} (la condición \texttt{>= 0} cuenta el cero como positivo).
  \item \texttt{oddOrPos([-3,-2,0,1,4])} devuelve \texttt{2} en lugar de \texttt{3} (la condición \texttt{\% 2 == 1} no detecta impares negativos en Java).
\end{itemize}

Esto demuestra que la nueva suite parametrizada preserva la capacidad de detección que ya tenía el conjunto de tests no parametrizado del TP1.

\section{Ejercicio 3}
\subsection{Objetivo}
Construir una suite completa para \texttt{StackAr}, con fixture compartido vía \texttt{@BeforeEach}, marcando explícitamente las secciones \textit{arrange}, \textit{act} y \textit{assert} y agregando al menos dos tests negativos. Completar \texttt{repOk()} con el invariante de representación pedido y testearlo.

\subsection{Modelo de la clase}
\texttt{StackAr} es una pila acotada implementada sobre un arreglo \texttt{elems} con un puntero \texttt{sp} al tope, donde:
\begin{itemize}
  \item $sp = -1$ representa la pila vacía;
  \item las posiciones $0, 1, \dots, sp$ contienen elementos válidos;
  \item las posiciones $sp+1, \dots, \texttt{elems.length} - 1$ deben estar libres (\texttt{null}).
\end{itemize}

\subsection{Implementación de \texttt{repOk}}
El invariante pedido se traduce naturalmente en cuatro chequeos:
\begin{lstlisting}[style=javastyle]
public boolean repOk(){
    if (elems == null) {
        return false;
    }
    if (sp < -1 || sp >= elems.length) {
        return false;
    }
    for (int i = 0; i < elems.length; i++) {
        if (i > sp && elems[i] != null) {
            return false;
        }
        if (i <= sp && elems[i] == null) {
            return false;
        }
    }
    return true;
}
\end{lstlisting}

\subsection{Correcciones sobre la implementación}
La construcción del invariante puso al descubierto dos problemas en el código provisto:
\begin{enumerate}
  \item \textbf{\texttt{pop()} no respetaba LIFO}. La versión original devolvía el nuevo tope (es decir, el elemento que quedaba después de decrementar \texttt{sp}) en lugar del elemento desapilado, y además no limpiaba la celda liberada. Esto, además de ser semánticamente incorrecto, violaba la cláusula ``$\forall i > sp: \texttt{elems}[i] = \texttt{null}$''. La versión corregida guarda el tope, lo limpia y decrementa el puntero:
\begin{lstlisting}[style=javastyle]
public Object pop() throws IllegalStateException {
    if (isEmpty()) throw new IllegalStateException();
    Object rv = this.elems[sp];
    this.elems[sp] = null;
    sp--;
    return rv;
}
\end{lstlisting}
  \item \textbf{\texttt{push} aceptaba \texttt{null}}. La cláusula ``$\forall i \le sp: \texttt{elems}[i] \neq \texttt{null}$'' es incompatible con permitirlo. Se agregó una validación que rechaza \texttt{null} con \texttt{IllegalArgumentException}.
\end{enumerate}

\subsection{Suite de tests}
Se cubren todos los métodos públicos. Cada test marca con comentarios el patrón \textit{arrange / act / assert}. Algunos ejemplos representativos:

\begin{lstlisting}[style=javastyle]
@BeforeEach
void setUp() {
    // Todas las pruebas parten de una pila acotada de capacidad 3.
    stack = new StackAr(3);
}

@Test
void popDebeRetornarUltimoElementoYReducirSize() {
    // arrange
    stack.push("A");
    stack.push("B");
    // act
    Object valor = stack.pop();
    // assert
    assertEquals("B", valor);
    assertEquals(1, stack.size());
    assertEquals("A", stack.top());
}

@Test
void pushConNull_debeLanzarExcepcion() {
    assertThrows(IllegalArgumentException.class, () -> stack.push(null));
}
\end{lstlisting}

Los tests negativos cubren al menos cuatro escenarios: \texttt{push} en pila llena, \texttt{push(null)}, \texttt{pop} en pila vacía y \texttt{top} en pila vacía.

\subsection{Tests de \texttt{repOk} y uso de reflexión}
Para probar las ramas \texttt{false} de \texttt{repOk} no alcanza la API pública: la clase no permite, por ejemplo, dejar \texttt{sp} con un valor imposible o un hueco en la zona activa. Se usó \texttt{java.lang.reflect.Field} para corromper el estado interno de forma controlada. Esta es una técnica que el libro discute al hablar de \textit{controllability}: cuando el código bajo prueba esconde su estado, hace falta un mecanismo adicional para forzar las situaciones que queremos verificar.

\begin{lstlisting}[style=javastyle]
@Test
void repOkConHuecoEnZonaActiva_debeRetornarFalse() throws Exception {
    stack.push("A");
    stack.push("B");
    Object[] elems = getElems(stack);
    elems[1] = null; // creamos un hueco
    assertFalse(stack.repOk());
}
\end{lstlisting}

\subsection{Inconvenientes encontrados}
\begin{itemize}
  \item No se puede romper el invariante desde la API pública sin recurrir a reflexión: para algunos casos negativos hizo falta tocar campos privados.
  \item Implementar \texttt{repOk} expuso el problema de \texttt{pop}, que no era visible mientras los tests sólo miraban el resultado del método aislado.
  \item \texttt{equals} usa la longitud del arreglo completo, así que dos pilas con misma capacidad y mismos elementos son iguales, pero dos pilas con distinta capacidad y mismos elementos no lo son. Es coherente con el modelo de pila acotada, pero conviene tenerlo presente al diseñar tests.
\end{itemize}

\subsection{Cómo ejecutar}
\begin{center}
\texttt{mvn -Dmaven.repo.local=.m2 -Djacoco.skip=true -Dtest=StackArTest test}
\end{center}

\section{Ejercicio 5}
\subsection{Objetivo}
Escribir tests parametrizados para \texttt{ZuneBug.currentYear(int days)}. Si los tests revelan alguna falla, hacer debugging y corregir el defecto.

\subsection{Contexto - el Zune bug}
\texttt{ZuneBug} reproduce un defecto real: el firmware del Zune calculaba el año actual a partir de los días transcurridos desde el 1 de enero de 1980. El 31 de diciembre de 2008 (año bisiesto) todos los dispositivos colgaron al entrar al bucle por la combinación de \texttt{days = 366} y \texttt{year = 2008}. El defecto era una combinación de \textit{off-by-one} en la guarda y una rama bisiesta sin \texttt{else}.

\subsection{Versión original}
\begin{lstlisting}[style=javastyle]
public static int currentYear (int days) {
    int year = 1980;
    while (days > 365) {
        if (isLeapYear(year)) {
            if (days > 366) {
                days -= 366;
                year += 1;
            }
            // sin else: si cae en este else implicito,
            // ni days ni year se actualizan -> loop infinito
        } else {
            days -= 365;
            year += 1;
        }
    }
    return year;
}
\end{lstlisting}

\subsection{Diseño de los tests parametrizados}
Se construyeron dos tests complementarios:
\begin{enumerate}
  \item \texttt{casosDeBorde} con \texttt{@MethodSource}, cubriendo valores específicos elegidos por análisis de bordes: \texttt{1}, \texttt{365}, \texttt{366}, \texttt{367}, \texttt{731} y \texttt{1461}.
  \item \texttt{currentYear\_debeCoincidirConOracle} con \texttt{@ValueSource}, que compara la rutina contra \texttt{ZuneBug.oracle}, una implementación de referencia basada en \texttt{LocalDate.plusDays}. Esto introduce la idea de \textit{differential testing} contra un oráculo confiable.
\end{enumerate}

Ambos tests envuelven la ejecución en una llamada del estilo \texttt{assert\-Timeout\-Preemptively(}\allowbreak\texttt{Duration.ofMillis(200))} para que un eventual loop infinito se traduzca en un \textit{failure} y no en un \textit{hang}.

\subsection{Fallas detectadas}
\begin{itemize}
  \item \textbf{Loop infinito} para \texttt{days = 366}: la guarda exterior \texttt{days > 365} se cumple, pero la rama bisiesta solo descuenta cuando \texttt{days > 366}. Como no hay \texttt{else}, el cuerpo del \texttt{while} no progresa.
  \item \textbf{Off-by-one} en transiciones exactas, por ejemplo \texttt{days = 731} y \texttt{days = 1461}: el método retornaba un año menos del que indica el oráculo.
\end{itemize}

\subsection{Corrección aplicada}
Se reescribió el bucle haciendo explícito cuántos días tiene el año que se está consumiendo:
\begin{lstlisting}[style=javastyle]
public static int currentYear (int days) {
    int year = 1980;
    while (true) {
        int daysInYear = isLeapYear(year) ? 366 : 365;
        if (days >= daysInYear) {
            days -= daysInYear;
            year += 1;
        } else {
            break;
        }
    }
    return year;
}
\end{lstlisting}
Mientras queden días suficientes para completar el año en curso, se descuentan y se avanza. Cuando no, se devuelve el año actual. La condición \texttt{>=} maneja correctamente los bordes y la rama del bucle siempre progresa, lo que elimina el loop infinito.

\subsection{Cómo ejecutar}
\begin{center}
\texttt{mvn -Dmaven.repo.local=.m2 -Djacoco.skip=true -Dtest=ZuneBugParameterizedTest test}
\end{center}
Luego de la corrección la suite reporta \texttt{Tests run: 21, Failures: 0, Errors: 0}.

\section{Ejercicio 6}
\subsection{Objetivo}
Implementar \texttt{repOK()} para \texttt{BoundedQueue} y verificar mediante tests parametrizados que el invariante se mantiene tras secuencias de \texttt{enQueue} y \texttt{deQueue}.

\subsection{Modelo de la clase}
\texttt{BoundedQueue} es una cola FIFO acotada, implementada como buffer circular. Los atributos son \texttt{elements} (arreglo), \texttt{size}, \texttt{front} (índice del próximo a desencolar), \texttt{back} (índice donde se escribe el próximo \texttt{enQueue}) y \texttt{capacity}.

\subsection{Invariante de representación}
Las cláusulas que valida \texttt{repOK} son:
\begin{enumerate}
  \item \texttt{elements != null} y \texttt{elements.length == capacity}.
  \item \texttt{capacity >= 0}.
  \item $0 \le \texttt{size} \le \texttt{capacity}$.
  \item Caso $\texttt{capacity} = 0$: \texttt{size}, \texttt{front} y \texttt{back} valen cero.
  \item $0 \le \texttt{front} < \texttt{capacity}$ y $0 \le \texttt{back} < \texttt{capacity}$.
  \item \textbf{Buffer circular}: \texttt{back == (front + size) \% capacity}.
  \item Zona ocupada sin huecos: para todo $i \in [0, \texttt{size})$, \texttt{elements[(front+i) \% capacity] != null}.
  \item Zona libre limpia: el resto de las posiciones son \texttt{null}.
\end{enumerate}

\subsection{Implementación}
\begin{lstlisting}[style=javastyle]
public boolean repOK() {
    if (elements == null) return false;
    if (capacity < 0 || elements.length != capacity) return false;
    if (size < 0 || size > capacity) return false;
    if (capacity == 0) return size == 0 && front == 0 && back == 0;
    if (front < 0 || front >= capacity || back < 0 || back >= capacity) return false;
    if (back != (front + size) % capacity) return false;
    boolean[] occupied = new boolean[capacity];
    for (int i = 0; i < size; i++) {
        int idx = (front + i) % capacity;
        occupied[idx] = true;
        if (elements[idx] == null) return false;
    }
    for (int i = 0; i < capacity; i++) {
        if (!occupied[i] && elements[i] != null) return false;
    }
    return true;
}
\end{lstlisting}

\subsection{Tests parametrizados}
Para no escribir un test por cada secuencia se utilizó un mini-DSL textual: \texttt{E:valor} representa \texttt{enQueue(valor)} y \texttt{D} representa \texttt{deQueue()}. Una cadena como \texttt{"E:a;E:b;D;E:c"} encadena las operaciones, y un método \texttt{apply} las ejecuta una por una, chequeando \texttt{repOK} en cada paso.

\subsubsection*{Escenarios válidos (\texttt{@MethodSource})}
Se cubren situaciones representativas: llenado y vaciado completo, wrap-around (cuando \texttt{back} da la vuelta al final del arreglo), capacidades chicas (1 y 2) donde la aritmética modular es más delicada.

\begin{center}
\begin{tabular}{lll}
\toprule
Capacidad & Operaciones & Cola final \\
\midrule
3 & \texttt{E:a;E:b;D;E:c}           & \texttt{[b, c]}       \\
3 & \texttt{E:x;E:y;D;E:z;E:w}       & \texttt{[y, z, w]}    \\
4 & \texttt{E:1;E:2;E:3;D;D;E:4;E:5} & \texttt{[3, 4, 5]}    \\
2 & \texttt{E:p;E:q;D;E:r}           & \texttt{[q, r]}       \\
1 & \texttt{E:solo;D}                & \texttt{[]}           \\
\bottomrule
\end{tabular}
\end{center}

\subsubsection*{Escenarios inválidos}
Las operaciones inválidas (\texttt{deQueue} en vacía, \texttt{enQueue(null)}, \texttt{enQueue} en llena) deben lanzar la excepción documentada y, además, el invariante debe seguir cumpliéndose después del error: una operación que falla no debe corromper la cola.

\begin{lstlisting}[style=javastyle]
@ParameterizedTest(name = "cap={0}, setup={1}, fail={2}, ex={3}")
@MethodSource("invalidScenarios")
void repOK_debeMantenerseCuandoUnaOperacionInvalidaLanzaExcepcion(
    int capacity, String setupOperations,
    String failingOperation, Class<? extends Throwable> expectedException
) {
    BoundedQueue queue = new BoundedQueue(capacity);
    for (String op : splitOperations(setupOperations)) {
        apply(queue, op, new ArrayList<>());
        assertTrue(queue.repOK());
    }
    assertThrows(expectedException, () -> apply(queue, failingOperation, new ArrayList<>()));
    assertTrue(queue.repOK());
}

\section*{Conclusiones}
\addcontentsline{toc}{section}{Conclusiones}
El práctico 2 consolida las herramientas introducidas en el TP1 y agrega dos ejes nuevos:
\begin{itemize}
  \item \textbf{Data-driven testing} con JUnit 5: separar los datos de los casos del cuerpo del test reduce la duplicación y mejora la legibilidad. \texttt{@CsvSource} es práctico para casos chicos e \textit{inline}, \texttt{@CsvFileSource} permite mantener los datos como recurso externo y \texttt{@MethodSource} es el camino natural cuando los argumentos no son primitivos o cadenas simples.
  \item \textbf{Invariante de representación como oráculo interno}: implementar \texttt{repOk} para \texttt{StackAr} y \texttt{BoundedQueue} expone defectos que los tests funcionales por sí solos no detectan. Es una técnica especialmente valiosa para clases con estado.
\end{itemize}

El caso del \textit{Zune bug} ilustra un patrón habitual cuando se hace debugging guiado por tests: los casos elegidos por análisis de bordes (\texttt{days = 366}) y el contraste contra un oráculo confiable (\texttt{LocalDate.plusDays}) bastan para localizar y luego corregir un defecto sutil. Para no quedarse esperando un cuelgue, conviene envolver la ejecución con un timeout preemptivo.
